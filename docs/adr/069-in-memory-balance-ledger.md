# ADR-069: 잔고 인메모리 원장 + 이벤트소싱 (Wallet 행 갱신 폐지)

- **Status**: Accepted (2026-07-15, §6 유저 확정 — 하단 "§6 확정" 참조). 2026-07-14 저녁 세션에서 방향 합의됨 ("원장을 먼저 잡되 빅뱅이 아니라 섀도 모드로"), 2026-07-15 구현 착수. **2026-07-16 S2 적용 완료** (S0 섀도 → 압축 게이트(kill -9 리플레이×2·quiesce 대조 0·check-integrity PASS) → truth 스위치 `LEDGER_TRUTH=true`). Wallet 행 락 소멸 실증 — 다음 병목은 Node 단일 프로세스(이벤트루프), 캠페인 기록: docs/test-reports/2026-07-16-adr069-ledger-s2-campaign.md.
- **Context 근거 데이터**: docs/specs/refactor-observations.md **#23** (2026-07-14 실측 붕괴 + 부하테스트), 관찰 #21 (경계 멱등성 갭).

## Context

2026-07-14 라이브 사고와 합성 부하테스트로 BE 처리량 구조 한계가 실측됐다:

- **병목의 정체 = 잔고가 "DB 행"이라는 것.** 주문 접수(동결)·정산(4-leg)·환불이 전부 `Wallet` 행 UPDATE라, 같은 유저·자산의 모든 흐름이 행 락에 직렬화된다 (pg_locks 108건 캡처 — BLOCKED 전원이 Wallet 동결 UPDATE, BLOCKER는 idle-in-transaction place tx). 단일 MM 계정 기준 상한 60~75 TPS 실측.
- 수술 ①(place tx 슬림)·②(컨슈머 6병렬)·③(워커 델타 배치)·인덱스·풀 상향으로 접수 ~200 TPS, 드레인 235/s까지 왔으나, **주문 1건 = Postgres ACID 쓰기 ~10회 + Node 단일 프로세스** 구조상 300~500이 천장. "거래소라면 300+" (유저 기준) 이상, 특히 수천 TPS는 구조 전환 필요.
- **매칭엔진은 이미 목표 아키텍처로 검증돼 있다**: inbound 토픽=WAL, compacted state 토픽=스냅샷, 부팅=스냅샷 복원+리플레이(기반영 skip) — bitshuriken-prod-match/main.py:6-8, messaging/snapshot_store.py. 당일 4회 재기동 전부 북 복구 정상.
- `SettlementEvent` 테이블이 이미 append-only 저널이다. 지금은 워커가 그걸 행 갱신으로 프로젝션할 뿐.

## Decision

1. **진실(truth)의 이동**: 잔고의 진실을 Wallet 행에서 **인메모리 원장 + append-only 저널**로 옮긴다. Wallet 행은 **비동기 읽기 프로젝션**으로 강등 (API 응답·FE·기존 툴 호환용).
2. **저널 규율이 §1**: 모든 잔고 변경(동결/해제/정산/환불/이체/입출금)은 저널 엔트리(전역 seq + sourceKey)로 먼저 기록되고, 원장 적용은 **리플레이 멱등** (같은 seq/sourceKey 재적용 = no-op). 관찰 #21(오프셋 커밋 vs 반영 원자성)은 이 규율로 해소된다 — 재전달·리밸런스·크래시 리플레이가 전부 같은 멱등 경로를 탄다.
3. **엔진 패턴 이식**: 원장 스냅샷은 엔진 snapshot_store와 동형 (주기 스냅샷 + 스냅샷 오프셋부터 저널 리플레이). REST 접수 경로의 동결도 저널 엔트리가 된다 (현재는 직접 행 UPDATE — 이 부분이 신규 저널화 대상).
4. **섀도 모드 마이그레이션** (빅뱅 금지):
   - Phase S0: 원장을 병행 가동, 기존 Wallet 경로가 계속 진실. **기존 정합성 하네스(F1~F4, ADR-059)가 원장 vs DB를 상시 대사** — 검증 인프라를 마이그레이션 안전망으로 재사용.
   - Phase S1: N일 무드리프트 + 재기동/크래시 리플레이 테스트(킬 -9 포함) 통과 게이트.
   - Phase S2: truth 스위치 (잔고 판정·주문 수락이 원장 기준), Wallet 행은 프로젝션.
5. **F1~F4 재정의**: F1(장부 대사)의 기준축이 "저널 리플레이 결과 vs 원장 vs 프로젝션" 3자 대사로 바뀐다. 드레인-후-측정 원칙(feedback-026)은 유지.

## 원장 이후에도 살아남는 병행 작업 (버려지지 않음 — 순서 무관하게 진행 가능)

- 정산 컨슈머+워커 **프로세스 분리** (토폴로지 — 원장 프로젝터가 살 집)
- **lastFillOf 제거** — fill 디테일을 TR→OU 메시지에 실어 전달 (메시지 계약; 원장에서도 필요)
- place 경로 **백프레셔** (행별/계정별 세마포어 + 초과 시 429 — 관찰 #23 플랜 ④)
- **MM 계정 심볼당 분리** (봇 설정, BE 무접촉)
- 스킵: TR 마이크로배치 (원장이 대체)

## Rationale

- 락 소멸 = 직렬화 상한 소멸: 원장 적용은 메모리 연산(µs), 저널 append는 Kafka/DB append-only(락 프리). 수천 TPS 경로.
- 이 코드베이스의 실증된 최약점이 재기동/복구 정합성(#21/#22, 07-14 사고 4병리)이므로, **복구가 어려운 아키텍처를 빅뱅으로 가지 않고** 기존 검증 자산을 다리 삼아 건넌다.
- 오더북은 변경 불요 — 이미 인메모리+WAL+스냅샷. 시스템의 난제는 원장 자체가 아니라 **엔진↔원장 경계의 정확히-한-번**이며, 저널 seq 규율이 그 답이다.

## Consequences

- (+) 잔고 경로 락·풀 경합 소멸, 수천 TPS 여지. 관찰 #21 클래스 버그의 구조적 해소. 실거래소 아키텍처와 정렬 (feedback-024).
- (−) BE가 상태ful해짐: 원장 프로세스의 스냅샷/리플레이/승격 운영 부담. 다중 인스턴스 수평 확장은 유저·자산 샤딩 설계 필요 (후속 ADR).
- (−) 전환기 동안 이중 쓰기 비용 (섀도 모드의 대가 — 의도된 것).
- (−) F1~F4·ADR-059 체커, check-integrity.sh, bots integrity 등 검증 자산 개정 필요.

## §6 확정 (2026-07-15, 유저)

| # | 정책 | 결정 |
|---|---|---|
| 1 | 저널 매체 | **(b) DB append-only 테이블** — 신규 `BalanceJournal` 모델 (ADR-067 교훈: 기존 모델 컬럼 추가 금지, 신규 테이블+enum만 pre-migration 안전). PG autoincrement가 전역 seq를 제공하고, place tx에서 Order INSERT와 원자 결합돼 이중 쓰기 경계(#21류)가 원천 차단됨 |
| 2 | 저널 내구성 | PG 동기 커밋 유지(현행과 동일). 그룹 커밋 등 튜닝은 측정 후 별도 노브 |
| 3 | 스냅샷 주기 | S0은 부팅 시 저널 전량 리플레이(현 규모 충분). 저널 성장 시 스냅샷 테이블 도입(후속) |
| 4 | REST 응답 시맨틱 | **저널 커밋 후 응답** — RPO 0. (b) 선택으로 오늘의 "tx 커밋 후 응답"과 동일 구조라 지연 증가 없음, 락 대기만 소멸 |
| 5 | 프로젝션 랙 | Wallet 행 프로젝터 목표 ≤1s, 5s 초과 시 경보 |
| 6 | failover 토폴로지 | **단일 인스턴스 재시작** (엔진과 동일 모델 — 크래시 시 저널 리플레이 복구). active-passive는 P4(멀티인스턴스)에서 재논의 |

**원장 소유 토폴로지**: be-spot = spot 지갑 원장, be-futures = futures 지갑 원장, portal은 저널 append만 하고 적용은 소유 앱의 저널 테일러가 수행 (이체 debit 등 콜드 플로우의 조건 검사는 소유 앱의 적용 시점 검사 + bounded 대기로 동기 API 시맨틱 보존).

**구현 범위 (2026-07-15 유저 지시)**: 목표는 **Wallet 행 락의 소멸**이다. 잔고 경로(동결/해제/정산 leg/환불/이체/입출금/펀딩/청산 leg)만 저널+원장으로 이동한다. **futures 포지션 회계(EP/flip/RPNL의 per-event 직렬 적용)는 불변** — 포지션은 Wallet 행이 아니라 컨보이와 무관하고, 경로 의존(비가환)이라 배치 불가가 본질이기 때문(관찰 #23 수술 ③ NO-GO 원인). 잔고 저널 엔트리는 금액 확정된 순수 증분(가환)이라 적용 순서 무관 — 잔고 충분성 등 조건 검사는 append 시점에 인메모리 원장에서 수행한다. 도달 목표: S0 섀도 → 압축 게이트(합성 churn 무드리프트 + kill -9 리플레이) → S2 truth 스위치(코드 설정 게이트, 가역) → M1 Mac 기준 균형 500+ TPS 실측.
