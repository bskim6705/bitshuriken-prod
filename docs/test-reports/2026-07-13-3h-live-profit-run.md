## 인프라 사건 (초기 ~1h 소요) → `scripts/exchange.sh` 신설로 봉인
1. **어제 세션의 좀비 감시 셸**(sleep 30/60 루프)이 스택 다운 감지 시 어제 버전(stale dist·bots·agentd)을 재기동 — 포트 선점·컨슈머 그룹 분열·유령 서브계정 AAVE 0.50 체결로 fresh DB 오염 → 좀비 제거 + 2차 리셋.
2. **Kafka 준비 전 토픽 auto-create 레이스** → spot out/book/state가 1파티션 생성, lane 매핑 파괴.
3. **macOS venv python ps 아티팩트**: ps가 프레임워크 경로(`MacOS/Python main.py`)로 표시 → venv 경로 pgrep 전부 오탐 → "엔진 죽음" 오판 반복 → **엔진 22개 스웜**이 파티션을 쪼개 알트 정산 블랙홀 (1차 리셋의 진짜 원인).
4. **인플레이스 토픽 재생성 후 stale 컨슈머 그룹 오프셋** → Kafka 연결 프로세스 전원(nest 3·엔진 2)이 ~3분 내 조용히 사망, dust refund 재소비 폭주. non-Kafka(FE·bots·agentd)는 생존 — 이 생존 패턴이 결정적 단서. 브로커 볼륨 초기화로 해소.
5. zsh `/dev/tcp` 미지원(항상 실패)으로 포트 체크 전부 오탐 — curl로 교체.

**교훈 → `scripts/exchange.sh`** (start/stop/reset/status): 각 단계 기능 검증(HTTP·pg_isready·파티션 수·엔진 인스턴스 수=정확히 1), 토픽 자가치유, 중복/잔재 자동 정리, 마커 argv 엔진 식별. reset→start→stop 풀사이클 실테스트 통과. CLAUDE.md How-to-run 갱신.

## 시간·토큰 소비 회고 (왜 3시간 창의 절반을 인프라에 썼나)
정확한 토큰 수치는 하네스가 노출하지 않아 계량 불가. 대신 소비를 키운 **행위**를 원인별로 기록 — 다음 런에서 반복하지 않기 위한 목적:
1. **거래소 리셋/재기동을 5~6회 반복** (좀비 재기동·엔진 스웜·stale 오프셋 사망이 매번 fresh DB를 오염시켜 재리셋). 리셋 1회 ≈ 3~5분 + 검증 왕복. → **exchange.sh가 이걸 1회로 압축** (근본 원인 4종 봉인).
2. **매칭엔진 로그가 rdkafka 경고를 한 줄에 수천 자 패딩**으로 뱉어 `tail` 한 번에 컨텍스트를 크게 먹음 → 이후 `cut -c1-N`으로 절단. (엔진 로그를 볼 땐 항상 절단할 것.)
3. **BE `SettlementService` DEBUG 로그가 "duplicate dust refund … skip"을 초당 수십 줄** 쏟아 로그 파일·읽기 비용 팽창. → 미결(로그 레벨 조정 후보).
4. **원인 오진 1건**: ps 오탐을 "엔진이 죽는다"로 읽고 재기동 루프를 돌린 것이 엔진 스웜을 낳아 1차 리셋을 강제. 상태 변경(재기동) 전에 신호(ps 표시)를 먼저 의심했어야 함.
5. **백테스트 매트릭스 13종을 인프라 복구와 병행** 실행 — 유익했으나 각 실행이 등록 로그를 반복 출력. 필요한 필드만 파싱하도록 조기 전환했어야.
요약: 토큰의 대부분은 **전략 실행이 아니라 인프라 함정 디버깅·재시도**가 먹었다. 그 함정은 이제 exchange.sh로 코드화됐으므로, 동일 목표 재실행 시 이 비용은 대부분 사라진다.
