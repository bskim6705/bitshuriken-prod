# Feedback-030: 다른 프로젝트에서 테스트를 이식할 때는 폴더 구조와 설계 문서를 함께 가져올 것

## Rule
다른 프로젝트의 테스트(또는 설계 산출물)를 이식할 때 테스트 코드만 옮기지 않는다. 원본의 폴더 구조와 각 테스트 옆의 설계 문서(`.md`)를 함께 이식하고, 이 프로젝트의 의미론에 맞춰 내용을 고쳐 쓴다.

## Why
설계 문서에는 "왜 그렇게 검증하는지"의 생각이 그대로 들어 있다 — 어떤 차원을 pairwise로 곱했는지, 왜 어떤 케이스를 방어 케이스로 뒀는지. 테스트 코드만 옮기면 케이스는 남고 근거는 사라져서, 나중에 테스트를 고치거나 케이스를 추가할 때 원래 의도를 복원할 수 없다. 폴더 구조는 그 차원(타입 × TIF × 책 상태)을 파일 시스템에 드러내는 장치라 함께 가야 한다.

## How to apply
- 이식 단위는 `test_x.py` + `test_x.md` 쌍. 폴더마다 `test_overview.md`로 차원과 철학을 적는다.
- 원본과 다른 의미론(예: STP 부재, FOK 사전 검사, 거부를 `status`로 표현)은 문서에 "원본 → 이 엔진" 대응 표로 남긴다.
- 쓰지 않는 차원의 폴더(예: `stp_none/`)는 만들지 않되, 왜 없는지를 overview에 적는다 (feedback-008).
- 적용 사례: `bitshuriken-prod-match/tests/{units,scenarios,invariants}` (2026-09-16), 색인 `tests/SCENARIOS.md`.
